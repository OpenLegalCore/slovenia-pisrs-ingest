# PIKI PostgreSQL and Qdrant data contract

**G2 candidate for owner review.** Database `pisrs_staging`, schema `pisrs`, PostgreSQL 18. The [API](PIKI-PISRS-API.md) defines source facts. The schema below defines intended migrations, not installed objects.

## PostgreSQL model

The proposed schema has **20 tables**, down from 29 in the review root. Each retained table protects an independent grain of identity, evidence, recovery or approval. Install the source subset at G3 and add the five index-specific tables at G4 after their approved prerequisites. Use views to expose the selected catalogue snapshot and the two published checkpoints.

| Consolidation | Why the retained state suffices |
|---|---|
| `catalog_source` and `source_manifest` | The immutable verified release pins the documented operations. Run evidence holds bounded ordered summaries. Durable attempts and occurrences retain independent row/hash-level proof. |
| `source_response`, `document_fetch` and `catalog_membership` | One retry row includes its response; document disposition is work state. Each occurrence keeps its provenance and one selected occurrence marks a member for that run and operation. |
| `reference` | One versioned resolution holds the typed edge and candidates. Identity events remain distinct to preserve explicit review and supersession. |
| `stage_checkpoint`, `index_publication_intent` and `embedding_delivery` | The generation stores publication intent. Checkpoints are the two committed run/generation heads. The immutable request/approval ledger stays separate from the per-input vector and current claim. |


In the table below, columns are required unless marked `?`. FK = foreign key, UQ = unique, PK = primary key, CK = check. Internal `bigint` IDs use identity columns. Digests are `bytea` with a 32-byte length check. Timestamps are `timestamptz` in UTC, legal dates are `date`, identifier strings use deterministic bytewise collation and preserve case and leading zeros. FKs use restrictive deletion by default. Check status fields against the states specified below or in [SYNC](PIKI-PISRS-SYNC.md). Attempt results use OPEN/HTTP_COMPLETE/HTTP_INCOMPLETE/TRANSPORT_ERROR/CONTRACT_ERROR/BODY_WITHHELD, occurrence validation uses VALID/QUARANTINED, parse state uses READY/QUARANTINED. All tables live in `pisrs`. Use only DB-generated ingest times for audit timestamps, and store upstream legal dates separately.

Raw HTTP entity means original application body octets with content coding, without TLS or chunked transport framing. Request `Accept-Encoding: identity`; if a coding is returned, store the received coded bytes and header, then decode separately with hard encoded and decoded size limits. Store full successful bodies including all envelope keys and root array elements. Safe error metadata is always recorded. Archive complete error bodies only when source rights and sanitization permit, using explicit `BODY_WITHHELD` otherwise. Never record authorization headers, cookies, credentials, or uncontrolled exception strings. `jsonb` is a query projection. A strict JSON reader detects duplicate keys, NULs and illegal types before JSONB conversion. Commit the raw body even if projection fails, record its failure, and keep that scope out of promotion. Use integer-preserving JSON and a versioned canonical serializer for value hashes (sorted keys, original sequence for arrays, lossless decimals, no Unicode normalization). JSON pointers use RFC 6901.

Namespaces are `RS_ACT`, `RS_NPB`, `LS_ACT`, `LS_NPB`, `EU`, `CODE_LIST`, `CODE_VALUE`. Normalize spec int64 IDs to canonical decimal text after exact integer validation. Retain the lexical source value in raw bytes. CELEX uses the original nonempty string. Projection and detail membership keep distinct endpoint provenance. Alternate IDs are time-varying attributes, no unique index or rewrite of old keys. A corrected numeric identity is a new record plus reviewed lineage evidence. Inferred NPB amending SOP, base SOP and ordinal are stored under the chosen rules revision in `reference_resolution.evidence` as `amending_sop`, `base_sop`, `version_ordinal` and `rule`, with literal null for unavailable values and `version_ordinal` a positive integer when present. A single raw record may yield new parse/resolution revisions without replacing earlier work. The supported definition of archival history is all observable versions and byte revisions since first acquisition plus all retrievable upstream NPB history at the accepted source boundary.

Operational constraints that span tables must be enforced in a transaction and independently audited. These include attempt/run/source provenance, eligible artifact-to-locator and response alignment, one coherent membership manifest, legal classification rules, finite vectors and generation completeness. Migrations introduce database/roles, archive and pinned contract, typed reconciliation, parser and text tables, then index ledger. A03/A11 cover selected-occurrence stability and historical replays. Acquire and publish the source and index heads independently. Apply each migration with lock and version/hash reconciliation. Back up before any migration that changes persisted semantics. Do not delete history to roll back a parser/schema interpretation.

## Binding migration, provenance and view rules

The 20-table inventory above is the **complete approved top-level persistence inventory**: **15 G3 archival/source tables** (`contract_revision`, `source_run`, `source_work`, `source_blob`, `source_attempt`, `source_record`, `record_revision`, `source_occurrence`, `reference_resolution`, `identity_event`, `document_locator`, `source_artifact`, `parsed_document`, `text_block`, `migration_log`) and **five G4 index/paid tables** (`index_generation`, `embedding_input`, `embedding_approval`, `embedding_request`, `index_member`). These are **logical schema requirements, not existing database objects and not executable SQL files**. A future migration implementation must not add separate checkpoint, manifest, response, document-fetch, publication-intent or vector-delivery tables. Instead use `source_run` (SOURCE publication and per-operation proof), `source_work` (document disposition), `source_attempt` (immutable response evidence), `source_occurrence` (selected current membership) and `index_generation` (G4 publication intent). Views may be added; they do not constitute persistent tables.

**Migration order and acceptance** (implement after G3 authorization):

1. Provision exactly `pisrs_staging` and schema `pisrs`. Create NOLOGIN schema owner and separate least-privilege migration, source, index, QA and backup DB roles, with tested negative grants. Storage/WAL binds are verified under `/data` before DB creation. `migration_log` is created first; each ordered migration runs under an advisory DDL lock, in one transaction where PostgreSQL supports transactional DDL, and records an immutable SHA-256. Re-executing an applied SHA is a no-op; an edited applied migration is a hard error. A failed migration rolls back rather than leaving a partly trusted schema.
2. In G3 create the fifteen archive tables in dependency order: `contract_revision`, `source_run`, `source_blob`, `source_record`, `record_revision`, `document_locator`, `source_work`, `source_attempt`, `source_occurrence`, `reference_resolution`, `identity_event`, `source_artifact`, `parsed_document`, `text_block`. `migration_log` precedes them. Establish deferred FK cycles only where necessary; a migrated schema must pass actual PostgreSQL catalog introspection before any live ingestion. Use explicit `ON DELETE RESTRICT` for immutable/source evidence.
3. In G4 add `index_generation`, `embedding_input`, `embedding_approval`, `embedding_request`, `index_member` under separate approved versioned migrations. Handle the `embedding_input.request_id` → `embedding_request` cycle by adding this FK after both tables exist, in the same migration transaction; do not omit it.
4. Every field without `?` is `NOT NULL`, except special externally enforced conditional/polymorphic columns explicitly explained in the inventory; nullable source fields remain nullable. `digest` means `bytea NOT NULL CHECK (octet_length(value)=32)` and the optional `digest?` means the same length check when nonnull. `raw_bytes bytea` must be checked against the independent hash and `byte_length`. Keep `jsonb` for indexed projection only; never use it to reconstruct alleged original API octets.
5. Enforce **composite provenance**, not merely independent FKs. An attempt's `(run_id, sweep, work_key)` references one work row; an occurrence's `attempt_id, run_id, source_key` must match that attempt's work and pinned operation; an artifact must have an archived matching complete response and matching verified locator namespace; `record_revision` belongs to the named record and contract. Add executable negative tests proving cross-run or cross-source joins cannot be introduced. If a constraint cannot be expressed as FK/CHECK, supply one narrowly scoped transaction-level validation plus a set-level independent audit; document exactly which are DB-enforced versus application-enforced.
6. The selected current-source view reads **only one successfully published source run** from `source_run`, then joins its `selected` validated occurrences to `source_record` and `record_revision` through the recorded attempt. It must not select `MAX(run_id)`, `MAX(record_revision_id)`, the last attempted page, or the latest HTTP body. Published rows are append-only; a new candidate cannot invisibly change a prior published snapshot. A consistency view exposes open/quarantined attempts separately.
7. The index-eligible view reads the selected SOURCE run, approved parser/chunker and validated legal windows; every candidate point has a deterministic `index_member`, cached `embedding_input` vector and an explicit link back to a `source_artifact`. Published vectors are recoverable from PostgreSQL without contacting the embedding provider. Before Qdrant mutation, verify the entire index membership and cached-vector set, not merely cardinality.
8. `source_run.PUBLISHED` is unique among active source runs (a partial unique index on the publication state), and `index_generation.PUBLISHED` and `index_generation.APPLYING` are each uniqueness-constrained. Use a single committed **published SOURCE head** and a separate committed **published INDEX head**; in-place updates must be fenced and checked against their prior generation. Never infer publication from `READY` or completed work counters.
9. Qualified key resolution uses `(namespace,parent_key,source_id)`, **not** SOP, MOPED, CELEX or a label as a globally unique key. Local code values' parent key is the dictionary identifier; numeric base-act and NPB locators use separate `kind`/namespace validation. A repeated source identity with changed metadata creates a `record_revision` and possibly an `identity_event`; it never rewrites the prior version's underlying bytes or legal dates. Duplicate/unknown keys remain in `source_occurrence` and retain source pointers.
10. Implement row-level access controls and backup capability as **roles and views on these tables**, not a second storage stack. G3 must prove fresh install, migration rerun, constraint rejection, role rejection, per-table index existence and complete archive restore. G4 proves cached-vector provenance, source/index checkpoint separation, index fence and paid-request UNKNOWN semantics. G5 proves real scheduled runs and timed off-host recovery.

### Coverage and identity projection contract

- **Collection identity**: each official operation is tracked separately, even where the same source record appears in several lists. The logical union counts distinct **qualified keys**, while per-operation membership counts each inclusion. Preserve distinct raw payloads and JSON pointers for duplicate observations. Compare the whole set of ten `/seznam` projections against their paired detailed catalogues under documented inclusion semantics; an equality mismatch is not silently excused by a matching count.
- **Text identity**: the exact stored locator set comprises source-authorized state-base and state-NPB numeric IDs proven to work in `/besedilo/{idZbirkaElement}`. Local and EU metadata are archived, but their full texts are **not supported by the verified integration API**. Such scope exceptions are counted separately and **must not** be reported as retrieved HTML. New official sources require a separate explicit owner scope decision.
- **History**: source version IDs, act IDs, document numbers, source legal dates, observed metadata revisions and actual byte revisions remain distinct. `first_run`/attempt timestamps represent ingestion observation, **not** legal validity or historical availability before first archive. Past consolidations that the API cannot return are **not** imputed. Preserve old `source_artifact` and `record_revision` rows after every rerun.
- **Date semantics**: legal validity, legal applicability, publication date, adoption date and observed-fetch date are distinct. A legal search asks “applicable at civil date D” only for a source-supported provision window; absence of a proven interval does **not** mean current or historical eligibility. Retroactive provisions and transitional exceptions require provision-level evidence; an ambiguous window is excluded from dated Qdrant retrieval but retained in PG archive with an explicit reason.
- **Exactness**: report separately (1) official endpoint inventory, (2) enumerated endpoint-qualified metadata identities, (3) full-array parity, (4) state document locator and fetched-body coverage, (5) observable history, (6) parser/provision coverage, (7) resolved/ambiguous references, and (8) frozen eligible vector points. A source without revisioned export or stable snapshot cannot justify a global point-in-time “100%” claim merely because two page sweeps match; report the maximum honestly verified envelope and time.

## Qdrant contract

One physical collection `pisrs_piki_staging`, with `text-embedding-3-large`, 3,072-dimensional unnamed float32 vectors and Cosine. PostgreSQL owns the eligibility manifest and cached vectors. Replay the same inputs and restore the same points from PostgreSQL. [Publication and recovery](PIKI-PISRS-SYNC.md#qdrant-publication)

| Scope | Search by date | Costs and operation |
|---|---|---|
| Current-only | Serves current text. Historical lexical/structured reads from PostgreSQL can still work. Historical semantic recall stays outside this index. | Fewer embedded inputs and points. Rollover may discard vectors for previously served versions unless cached in PG. |
| Current and qualified historical versions | Semantic retrieval across supported dates. Current search uses today's legal date with the same temporal filter. | More unique chunks, points and storage. Exact text reuse deduplicates embedding costs across versions, with a separate point for each legal context. One collection, one publication pipeline. |

**Owner-approved index policy (2026-11-16, OLC-91).** Index current and historically qualified state versions whose legal applicability for the selected date is evidenced. Preserve all retrievable history in PostgreSQL. Retain unsupported or unresolved windows as explicit gaps and exclude them from dated search. This is the G2 architecture decision. G4 paid approval remains separate and binds measured unique missing input tokens, a current tariff, transfer scope and cap.

### Legal date eligibility

- The caller selects a civil date in Europe/Ljubljana; the default is today. PostgreSQL derives legal windows under a versioned evidence rule and records whether the result is applicability or validity. They are distinct concepts. Publication, source observation and NPB document dates remain provenance. No legal window is inferred solely from consolidation order, title or document date.
- Normalize approved boundaries to half-open day intervals `[from_day, to_day)`, using integer days from 1970-01-01. Convert an inclusive end only when the source meaning is known. A verified open end uses `open_end=true` and no `to_day`. Unknown endpoints have a distinct unresolved disposition. Preserve the underlying dates, rule and evidence.
- Default search answers what text applies on the selected date under the approved rules and evidence available to the archive. If the question is historical knowledge as of a publication cutoff, that is a separate mode; use publication/observation constraints only when explicitly requested and supported. Handle retroactivity, transitional provisions and applicability after repeal under separately approved rules. If a version contains provisions with different windows, split at those boundaries or exclude the unresolved span from dated search. A mixed or ambiguous span cannot inherit dates from a sibling. Return traceable gaps from PG, with no nearest-version substitution.
- Qdrant uses a nested window filter so start and end constraints apply to the same window object. Match requested `kind`, then `from_day <= date` and `to_day > date` or verified `open_end`. The query path rechecks each returned point against the published PG generation, window and requested date. Time coverage is evaluated per supported legal scope. [Qdrant filtering](https://qdrant.tech/documentation/search/filtering/)

Point ID = UUIDv5 under RFC 4122 URL namespace over UTF-8 canonical compact JSON array of `["urn:openlegalcore:pisrs:piki:point:v1", locator_kind, source_id, raw_sha256_hex, parser_revision, chunker_revision, chunk_ordinal, model, dimensions, text_sha256_hex]`. A legal-date or link correction updates payload and provenance while retaining the input cache key. All fields are present unless their row specifies the optional endpoint of a verified open interval.
