# PIKI staging operations

**G2 candidate runbook.** Procedure names below describe future commands and unit work. Installation, service actions, database changes, all-source ingest and paid requests require their respective approved gates.

## Release and first start

1. Verify [G0–G2 evidence](PIKI-PISRS-ACCEPTANCE.md), approved repository baseline, approved G3 window, effective Docker/containerd roots, port/firewall reservations, `/data` capacity, private issuer-authorized secrets and independent backup destination. Record Git commit, wheel/dependency hashes, PostgreSQL/Qdrant image digests and schema/rules/parser hashes in one release manifest. Stage the immutable release under the [approved paths](PIKI-PISRS-ARCHITECTURE.md#network-and-files).
2. In the approved G3 window the operator creates only the declared PIKI-owned directories, users, bridge, PG/Qdrant containers, config and unit definitions. Apply owner, mode and container UID mapping before starting. Validate systemd files with the installed systemd version, ensure there are no anonymous volumes, confirm the actual container bind/storage and WAL paths, protect credentials and install controlled policies for restart and shutdown.
3. With timers disabled, start only the candidate stores. Preflight startup, DB and schema identity, read-only and writer grants, Qdrant TLS/auth and candidate collection behavior, mount/write manifests, active service users and negative cross-project access. Exercise the local QA tunnel in a restricted smoke test. Enable the source role only after these checks succeed, then run one bounded supervised source job. Continue the approved initial archival pass under [SYNC](PIKI-PISRS-SYNC.md), validate parity and do a fenced capture/resume drill.
4. With owner approval and measured tokens, enable the index sender for the frozen plan, verify the candidate and publish the alias. Stage only the previously verified source/index releases behind read-only QA access. Enable timers after supervised validation and evidence of available recovery paths. G5 requires a genuine scheduled run, controlled failure and isolated recovery, then grant test-user access.
5. For release updates, match pinned hashes, fence writers, take a verified pre-change backup and snapshot if available, apply forward-compatible migrations, atomically activate the intended release and verify dry/preflight and readback. On failure disable affected dispatch and restore or roll back only to a compatible previously verified release. Inspect record revisions before replay. Keep both checkpoint anchors and any unsettled paid requests.

## Runtime and health

The three jobs declared in [Architecture](PIKI-PISRS-ARCHITECTURE.md#components-and-boundaries) emit redacted JSON logs on `/data` with run, stage, release, spec hash and source key. Source preflight checks TLS, permitted profile, PG role and PIKI mount; index checks approval/budget and Qdrant identity; backup checks fence and space. Use local health probes and existing approved host alert delivery. Startup health checks are bounded and verify readiness, not process existence. Prefer stage-specific one-shot failures with durable work and safe delayed retry over unconditional restart loops. Remediation can retry the same run/generation under the same contract.

- Alert on contract/identity/quarantine failures, auth/proxy errors, expired credential/cert or approval, unexpected aliases, ledger UNKNOWN paid requests, backup/restore or integrity failure and low disk before allocating more. For ordinary pending approvals show the index as blocked, with the previous verified generation still serving if available.
- Report time of last published source run and index generation, lag and oldest outstanding item, counts per reason, read/retry bytes and latency, archive and Qdrant parity digests, disk/WAL/vector peaks, remaining budget and backup manifest ID. Candidate thresholds are one expected schedule plus grace, any integrity failure, 20% free disk floor and budget refusal before overspend. Tune latency and freshness against the verified schedule and entitlement.
- For full disk, stop new staging work and preserve manifests. Use evidence to identify old PIKI-owned disposable scratch or approved retired generations and recover capacity only in the approved scope. Never move global data or use image/volume prune. For PG outage use durable work states rather than a wall-clock reset. For Qdrant outage queue no new publication, recover the verified alias and required points from PG. For permission/TLS failure route to the responsible operator with stage/hash/status, keeping credentials private.

## Backup and restore

Candidate SLO is one successful fenced capture every 24 hours with last verified baseline retained, RPO ≤24 hours and measured RTO ≤8 hours for PostgreSQL archive and the formerly served index. Retain seven daily and four weekly encrypted recovery sets subject to capacity and legal policy. Validate with real measured backup and restore time before acceptance. Backup and isolated restore each include their temporary space beneath `/data`. Copy encrypted backups to an approved independent failure domain. Capture just the staging namespace and approved metadata.

1. Acquire exclusive backup fence. Refuse capture with an in-progress alias switch, an unverified serving generation or a pending contradictory checkpoint. Establish a consistent PostgreSQL dump for `pisrs_staging` in custom archive format including archive blobs, run ledgers, cache vectors, both checkpoints and migration metadata. Record separately sanitized role/grant definitions and required extension versions. No role secrets in dump. Create a supported Qdrant snapshot of the exact committed serving collection and record alias mapping and collection config. If G3 precedes an index, record index NOT_RUN in the manifest.
2. Create a manifest tying dump/snapshot byte hashes, release/spec/schema/profile digests, last SOURCE/INDEX checkpoint proof, relation and record manifests, active alias/generation and UTC capture time. Include the separate paid-request uncertainty journal and relevant provider references. Keep that journal on approved recoverable storage with point-of-no-return intent written durably before gated paid dispatch. Do not accept recovery as allowed to re-send the gap since the last protected capture. Verify files, encrypt, finalize manifest, transfer to the independent location and verify receiver-side integrity before reporting success. Release fence. Store crypto keys separately, restrict retention changes and regularly verify retrieval.
3. Restore only per explicit restore authorization. Provision isolated fresh mounts under `restore/<drill-id>/`, no live binds, secrets, public ports, application timers or outbound network. Use compatible pinned PG/Qdrant versions and dedicated recovery roles. Verify manifest/decrypt before restore; recreate roles safely then restore DB and Qdrant from the captured images. If Qdrant snapshot is unavailable or invalid, rebuild the index from the cached approved PG vectors with durable plan provenance and zero paid calls. Reconstruct the alias only from manifest and ledger agreement.
4. Independently read back full table counts, FK/unique/check definitions and validation status, all required identity and raw SHA-256 sets, parser/eligibility and checkpoint state. Verify exact Qdrant point IDs/payloads and vectors against PG under [SYNC](PIKI-PISRS-SYNC.md#qdrant-publication). Verify versions, no unrelated resources, measured RPO/RTO, sealed report and zero paid requests. Inject a controlled corruption/omission in a test fixture and require failure. Freeze restored work and compare paid intents with provider and protected out-of-band ledger before any resumption. A failed restore blocks G5.
5. A production-like PIKI recovery switch requires operator signoff with traffic stopped and a tested old-target rollback. Verify TLS, scoped readers, restored stage markers and alias, then gradually restore approved timers. Keep recovery evidence and delete only inspected, labeled recovery workspace after retention approval.
