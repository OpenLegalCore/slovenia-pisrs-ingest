# PIKI staging operations

**G2 candidate runbook.** Procedure names below describe future commands and unit work. Installation, service actions, database changes, all-source ingest and paid requests require their respective approved gates.

## End-to-end release and operational command contract

The following is an **implementation contract**, not evidence that commands or binaries already exist. Actual entrypoints are to be supplied by the G3 code release and verified in the release manifest; do not paste imaginary executable names into an operator console. Only one source package, the existing Docker Engine and the three approved one-shot units may be used. Deploy the archived/source half in G3; add Qdrant and the paid/index half only in G4.

| Stage | Required operator-visible action | Exact successful exit/proof | Stop and rollback boundary |
|---|---|---|---|
| G3 package | Build wheel + locked dependencies for the tested Python version, verify hash and clean source tree; stage immutable release on /data/pisrs-staging/releases/<commit> | Package metadata, locked hashes, target Python import/CLI --help smoke and nonroot ownership match the reviewed commit | Build mismatch: no activation or migration |
| G3 stores | Record Docker image SHA digest, existing daemon /data roots, no shared container conflicts, operator-approved bind ownership and isolated mounts; create only the declared PostgreSQL container/network | PostgreSQL responds on approved loopback and one database name/schema; WAL and every writable bind proven inside /data | Unexpected volume/root/port or public listener: disable staging before any ingestion |
| G3 schema | Run reviewed migrations with lock, checksum and PostgreSQL catalog assertions against the empty staging DB; test wrong DB, illegal data, read-only QA | Precisely 15 archive tables, PK/FK/unique/check, immutable raw SHA-256, constrained role grants, migration checksums | Partial migration or wrong role: stop, roll back database transaction; never repair by touching Medo |
| G3 source | Use the valid owner-confirmed token, bounded conservative configurable request pace and 429 handling; supervised GET then all scoped source/locator operations | Sealed SOURCE head, all 26 GET classes accounted, full raw/parse/history/PG parity A01–A11 | Any required gap/unstable sweep/limit/lock failure: archive attempts and retain old checkpoint |
| G3 local recovery | Fenced protected PostgreSQL archive capture under /data, independent readback and tested isolated local restoration; no remote destination required before OLC-94 | Local restored PG manifests and originals verified; do not call this independent disaster backup | Failed local restore fails this test; unknown remote location is `DEFERRED_OLC94` |
| G4 index | Deploy Qdrant image/one collection, five approved index tables, local token cost plan and separate explicit paid approval; cache validated vectors in PG | Exact point manifest and vector/payload parity, actual Qdrant health, in-place fence held during writes | UNKNOWN paid response: no auto retry; index stays old/blocked, restore from cached PG |
| G5 automation | Enable one timer after supervised runs; verify actual scheduled SOURCE→INDEX (if approved)→BACKUP chain; test alert and missed-run handling | Recorded genuine schedule evidence, two independently verified heads, accepted freshness, healthy recovery and dated QA query | Failed dependency must trigger alert and backup, never silently publish success |
| G5 local restore drill | Restore local protected PG archive in isolated /data mounts without paid network, rebuild Qdrant from PG vectors, verify originals/roles/both heads/corruption | Timed local parity and zero paid requests; off-host disaster recovery is `DEFERRED_OLC94` | Local restore/point parity failure blocks G5; true remote RPO/RTO tested later under OLC-94 |

**Rollback discipline:** before a release or migration switch, protect the last sealed SOURCE and INDEX heads and obtain an independently readback-verified protected local PG capture; true off-host backup only after OLC-94 approval. A failed candidate does not delete archived historical evidence or silently move a head. Recovery may restore a previously verified archive/manifest under explicit operator authorization; it must never overwrite Medo, global Docker configuration or unrelated PIKI volumes.

**Daily chain:** The single timer starts source, then index only if G4 is approved, then the third approved one-shot backup unit. Before separate OLC-94 activation that unit may make an authorized locally protected fenced capture/readback or explicitly record `DEFERRED_OLC94`; it **must not** transfer to remote storage, claim independent restoration or create external charges. Failures still invoke/report this stage; a failed source/index run is never converted into a successful publication by an old index or local capture. Report last attempted, last verified SOURCE/INDEX, last local capture and true independent off-host backup separately.

**Recovery is an explicit later owner decision:** independent encrypted remote destination/custodian/retention and RPO/RTO are **UNDECIDED and DEFERRED** to [OLC-94](https://linear.app/openlegalcore/issue/OLC-94) after full sync including separately approved Medo upgrade. No remote backup provider or location blocks documentation acceptance or G3 source ingest. Local fenced capture, rollback and isolated restore tests remain required and cannot be misrepresented as off-host recovery.

## Release and first start

1. Verify [G0–G2 evidence](PIKI-PISRS-ACCEPTANCE.md), reviewed exact commit and distinct G3 authorization, Docker/containerd roots and port isolation, /data capacity, the protected existing PISRS token, conservative request/byte limits and local fenced capture/restore capacity. Do not demand a new issuer letter or off-host destination. Record immutable release/image/schema hashes under [project paths](PIKI-PISRS-ARCHITECTURE.md#network-and-files).
2. In the approved G3 window the operator creates only declared PIKI-owned paths, accounts, network, PostgreSQL container, application units and data binds. Verify effective mount ordering, runtime numeric UID/GID, actual WAL/storage locations, no anonymous volumes and least-privilege grants. Start PostgreSQL with the timer disabled. Confirm scoped access and negative cross-project tests before any source write.
3. Run one bounded supervised source job, then continue scoped complete source capture/parity under [SYNC](PIKI-PISRS-SYNC.md). Confirm checkpoint recovery and take/read back a protected fenced **local** PostgreSQL capture. Prove local restore at the relevant gate. Do not call this independent disaster backup. G3 has no Qdrant dependency.
4. In G4, validate the one Qdrant container and staged collection under the approved topology. Confirm complete cached-vector rebuild rights and restricted QA. Enable the paid sender only after a separate owner-approved token plan. Publish under the PG fence and validate the one-collection update and recovery. Perform an isolated recovery drill, then activate the timer and native stage dependencies for G5 acceptance. Admit test users after actual scheduled-run and recovery evidence.
5. For updates, fence writers and QA if necessary, verify pinned release hashes and take a readback-verified pre-change PG backup. Apply forward-compatible migrations, activate the versioned release and verify parity. Roll back only to a compatible verified release. Preserve archived revisions and both committed heads.

## Runtime and health

The three one-shot jobs declared in [Architecture](PIKI-PISRS-ARCHITECTURE.md#components-and-boundaries) emit redacted JSON logs on `/data` with run, stage, release, spec hash and source key. Source preflight checks TLS, permitted profile, PG role and PIKI mount; index checks approval/budget and Qdrant identity; backup checks fence and space. Use local health probes and existing approved host alert delivery. The single persistent timer starts the source unit. After activation, a failed source starts backup directly; a successful source starts index; index completion or failure starts backup. Disabled or unapproved index work exits cleanly and still hands off to backup. Set finite time limits and alarm if no backup is produced by its daily deadline. Manual starts use the same chain after activation; before activation, start the stages individually. Each job checks its role, lock and durable progress independently. Retry the same run/generation under the same contract.

- Alert on contract/identity/quarantine failures, auth/proxy errors, expired credential/cert or approval, a stuck index publication fence, ledger UNKNOWN paid requests, backup/restore or integrity failure and low disk before allocating more. For ordinary pending approvals show the index as blocked, with the previous verified generation still serving if available.
- Report time of last published source run and index generation, lag and oldest outstanding item, counts per reason, read/retry bytes and latency, archive and Qdrant parity digests, disk/WAL/vector peaks, remaining budget and backup manifest ID. Candidate thresholds are one expected schedule plus grace, any integrity failure, 20% free disk floor and budget refusal before overspend. Tune latency and freshness against the verified schedule and entitlement.
- For full disk, stop new staging work and preserve manifests. Use evidence to identify old PIKI-owned disposable scratch or approved retired generations and recover capacity only in the approved scope. Never move global data or use image/volume prune. For PG outage use durable work states rather than a wall-clock reset. For Qdrant outage queue no new publication, recover the verified serving manifest and required points from PG. For permission/TLS failure route to the responsible operator with stage/hash/status, keeping credentials private.

## Backup and restore

**Real independent backup is DEFERRED to [OLC-94](https://linear.app/openlegalcore/issue/OLC-94); LOCATION UNDECIDED.** The procedure below is a FUTURE technical recovery proposal only, not an active remote endpoint, provider order, required G2/G3 grant or substitute for the current local fenced recovery tests. The owner will decide remote location/custodian/retention and tested disaster recovery after proven full sync on PIKI and separately upgraded Medo. Until then no off-host transfers, paid storage or independent-backup PASS. Two local copies are not an independent backup.

- Encrypt before upload using the recovery custodian's public key and transfer over authenticated TLS. Keep the private recovery key outside PIKI with escrowed independent recovery access. The backup service may create uniquely named objects in its PIKI prefix and cannot delete, overwrite or shorten retention. A separate verifier reads ciphertext to check object receipt/hash; the recovery custodian can read and decrypt. Storage administration and retention changes use the separate operator account. Require retention enforcement at the destination.
- **Future OLC-94 proposal, NOT APPROVED:** possibly retain seven daily and four weekly encrypted, independently readback-verified sets and target RPO ≤24 h / RTO ≤8 h. Actual provider, location, custodian, retention and objectives are owner decisions made at OLC-94 activation. Do not provision or budget remote storage or require remote rights before G3 source writes. Real off-host isolated restore evidence belongs only to later OLC-94.

1. Acquire the exclusive backup fence and record settled published source and index heads. If a crashed index remains APPLYING, capture the archive and its intent with an explicit index-recovery-required disposition. Use the last verified index manifest for restore until the interrupted candidate is reconciled. Dump `pisrs_staging` in custom archive format with original bytes, run/role-relevant ledgers, manifests, all completed cached vectors and migration metadata. Record compatible roles and software versions in a sanitized manifest. No Qdrant snapshot or Qdrant backup credential is needed. G3 captures legitimately have INDEX NOT_RUN.
2. Hash the dump and record both checkpoints, original byte/dataset digests, previous verified index manifest, exact collection config and release/spec/schema/profile revisions. Encrypt, transfer and independently read back the backup, then publish its timestamp/hash and retention status. Keep encryption material separate. A proven full recovery is required to accept the RTO.
3. Restore using separately authorized isolated PIKI mounts below `restore/<drill-id>/`, no live binds, public ports, timers or paid network. Recreate reviewed roles, verify and restore PG, then rebuild the fixed staging Qdrant collection from the last verified PG point manifest and cached vectors. Verify exact ID sets, payloads and vectors before opening the read fence. Test corrupted/truncated fixtures and measure duration. A legacy pre-existing Qdrant collection is never a recovery input.
4. Keep paid sending disabled after recovery. Review restored claims and provider/operator records covering the interval since capture. An unknown or missing charge outcome is never retried automatically. Explicitly resolve the gap and obtain a fresh approved plan when needed. Recovering the accepted index itself uses zero paid requests.
5. A real recovery switch requires operator signoff, stopped traffic, a compatible tested rollback and negative access tests. Restore approved job dependencies only after archive and index parity. Keep the recovery evidence and clean only the inspected recovery workspace when its retention allows.
